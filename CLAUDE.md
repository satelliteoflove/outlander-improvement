# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An improvement hack of the SNES game *Outlander* (Mindscape, 1993) that adds the SA-1 enhancement chip to fix its poor framerate. Priorities, in order:

1. Framerate in the driving scenes: smooth, 30 fps if possible, without changing how the game plays or making it harder.
2. Making it less of a chore to play (begun: Gameplay changes, below): fewer roadblocks, less collision damage, faster walking, and the on-foot hit detection. No new art. Chris wants all of it in the one patch, not a separate optional one.

Chris wants `mesen2` used as the emulator for this work.

## The ROM

`Outlander.sfc` is the unmodified original and is the only input. It is copyrighted, so it is git-ignored and must never be committed or uploaded anywhere. The hack is to be distributed as a patch against it (`xdelta3` is installed; `flips` is not).

Never modify `Outlander.sfc` in place. Build outputs go to `build/`.

| | |
| --- | --- |
| SHA-1 | `4dd01cd2f950b70bd08a6b16115cd647c7147c04` |
| Size | 1,048,576 bytes, no copier header |
| Title / region | `OUTLANDER`, USA (NTSC), version 0 |
| Map mode | `$30`: LoROM, FastROM |
| Cart type | `$00`: ROM only, no SRAM |
| Checksum | `$E5AF` (valid) |
| Reset | `$00:8000`. Start-up code runs in bank `$00` (slow mirror) and calls into `$81` and up with `JSL` |
| NMI / IRQ / BRK | `$8111` / `$82CA` / `$8105` (native); emulation NMI also `$8111` |

File offset to address: LoROM, so offset `N` is bank `$80 + (N >> 15)`, address `$8000 + (N & $7FFF)`. The header is at file offset `$7FC0`.

Things found by a raw byte scan (not a disassembly, so treat as leads):

- The ROM is essentially full. The largest run of fill bytes is about 2.5 KB at `$82:CD00`; nothing else exceeds 770 bytes. New code needs an expanded ROM, which the SA-1 conversion requires anyway.
- `MEMSEL` (`$420D`) is written once, near file offset `$D78B`.
- There are about 9 stores to the S-CPU divider (`$4204`) and 1 to the multiplier (`$4202`). These registers do not exist for the SA-1 and any routine moved to it must use the SA-1's own arithmetic unit (`$2250`-`$2254`, result at `$2306`).

## How the game's driving scene works

Found by tracing; addresses are in the original ROM. Bank `$00` and `$80` are the same ROM bank (slow and fast mirrors); the main loop runs in `$00`, its subroutines mostly in `$80`/`$81`.

- Scene set-up is at `$00:8C02` and falls into the main loop at `$00:8C54`. After an on-foot stage the drive is set up elsewhere and the loop runs in the fast mirror, `$80:8C54` (the patch's `head_hook` returns to `$00`, which only makes the loop head slower to fetch). The loop head waits for at least two NMIs (`$2B`) and for the previous frame to have been shown (`$2E`, `$C5`), so the game itself caps at 30 fps.
- The view is software-rendered. The original takes about 7.3 vblanks a frame (8 fps): `JSL $81CC3B` at `$00:8E11` (road: projects 200 road segments and builds HDMA tables, 4.5 vblanks) and `JSL $809DD6` at `$00:8ED3` (objects: scaled sprites drawn into a tile frame buffer, 1.5 vblanks). The code between them (`$809A18`, `$81B7E9`, `$80AE1E`) also draws into the frame buffer and feeds the object renderer.
- The frame buffer is `$7E:30E5-$70E4`. The NMI handler (`$00:8111`) sends it to VRAM a piece at a time (at most `$0C00` bytes per vblank, routine at `$00:8515`) *while the renderer is still drawing*: `$DF` is how far the renderer has got, `$E1` how far the upload has. When the main loop sets `$C5` the handler sends the rest and flips to the other VRAM page (`$00:81B3`).
- The game uses low RAM only up to `$07FF` (stack near `$03FF`), with the direct page switching between `$0000` and `$0100`, and all of `$7E:2000-$7F:FFFF`. `$7E:0800-$1FFF` is never touched after boot.
- **Game speed is tied to the frame rate.** `$81B28A` runs the car's physics once per pass of the loop and sets `$AE` (distance for this pass, from speed) with no reference to elapsed time; `$00:8DF2` then steps the road `$AE`/4 times. Anything that makes passes faster makes the game faster, and so harder. The patch therefore runs one pass ("game step") per four shown frames and draws the three in between itself (In-between frames, below).
- **A pass, in order** (`$00:8D12` on): `$81B0E4` steers (the car's place across the road `$B9`, its change `$BB`, steering rate `$B7`, horizon `$B1`; it uses the `$AE` of the pass before), `$81B28A` is the engine (gears, revs, the new `$AE`), `$81B50D` fuel and odometer, `$809132` the gauges' needles, `$90B273` the status display; then the road is stepped (`$00:8DD3`), drawn (`$81CC3B`), scenery is spawned (`$809A18`), the gun at the side window is fired and drawn (`$00:9751`), and the object pass (`$809DD6`) moves, collides and draws every object. After `INC $C5` come the enemies' decisions (`$80C309`) and a few more (`$81AFD0`, `$81B5E9`, `$81B68F`).
- **The road** is a ring of 200 segments in three arrays (`$7E:2596`, `$2726`, `$28B6`: x, height, stripe), written at `$70`, which steps down; a second ring of 100 behind the car (`$2A46`, `$2B0E`, `$2BD6`; `$72`) serves rolling backwards (`$017A`, `$81CB5F`). A step (`$81CA0B` works out the next segment, `$81CAE5` stores it) moves the car one segment; `$B0` holds the quarters left over, and the renderer uses it, so the road moves in quarter segments. The renderer starts 17 entries behind `$70`, and rewrites the two x arrays in place as it draws (the road's x values are moved to where the car is; `$7E` carries the shift to the segments still to come). All distances in the game are in these quarters.
- **Objects**: 56 records of 12 bytes at `$7E:7121` (distance, type, x, flags, ...; type negative = free), drawn in the order of the list at `$73C1`, which the object pass sorts first, by the distances of the pass *before*. The pass then, record by record: adds `$FD` = -`$AE` (+ `$017A`/4) to the distance, tests for a collision with the car (`$80B845`), and calls the type's drawing routine (tables `$809F5C` far, `$809F80` near). Type 4 is an enemy vehicle: a record of `$3A` bytes at `$75B1` (five of them), a state machine (`JSR ($C76A,X)`) that moves it and leaves `$F9`/`$CF` for its drawing code. Type `$0A` adds a step of its own (`$7537`). Type `$0B` is a thrown object whose flight is worked out *inside its drawing routine* (`$80AC0B`, state at `$7571`). So logic and drawing cannot be told apart by routine.
- **Sprites and tiles**: scaled sprites are drawn as tiles into the frame buffer (`$DD` = next tile slot x 2, `$DF` = bytes used, from the table at `$80DE02`) and listed in one sprite table at `$7E:2D36` (4 bytes a sprite, size/high-x bits from `$2F36`; `$C6` = sprites used, starting at 4: the first four are the gauges' needles). The NMI handler sends `$C6` sprites and hides the rest. Both start afresh every pass (the loop head resets the counters); the gauges' tiles and sprites at the head of each persist.
- The NMI handler dispatches on `$00` (0 = driving). The driving path splits the screen with IRQs (`$00:82CA`, routines from the table at `$00:830C`, index in `$35`): each waits for horizontal blank, writes its registers and sets the line of the next. HDMA channels 0 and 1 read tables the road renderer builds, alternating between two buffers (`$2C`); the handler points them at the new ones when it flips. The on-foot scenes' main loop is at `$90:824A` and runs at 60 fps with most of the frame idle.
- Wasteful things worth knowing about: `$81D17B` builds a 16x16 multiply from PPU 16x8 multiplies about 300 times a frame, with a retry in case the IRQ handler used the multiplier meanwhile (flag at `$FF`); `$81DB9E` (send a sound command) busy-waits on the sound CPU, around 500 loop iterations a call.

## Architecture of the patch

The original game keeps running on the S-CPU. In the driving scene, the body of the main loop ("the block", `$00:8D12` up to the jump back to the loop head at `$00:8F14`) runs on the SA-1 instead, from a patched second copy of the ROM. The loop head (wait for the last frame to be shown, pause handling) and all interrupt handlers stay on the S-CPU. Nothing else in the game is remapped; the on-foot scenes execute no patched code at all (but for one hook in their set-up, `foot_nmi_on` below).

ROM image, 4 MB, built by `tools/build.py` (mapping `sa1rom 0,1,0,3`):

| Block | Banks | Contents |
| --- | --- | --- |
| 0 | `$00-$1F`, `$80-$9F` | The original game plus hooks. The S-CPU runs this. |
| 1 | `$20-$3F` | A second copy of the game, patched so the SA-1 can run it. Same addresses, so in-bank jumps need no fixing. |
| 3 | `$A0-$BF` | New code, `src/`. (FXB defaults to block 3 at power-on, which is why the reset hook can jump there.) |

Memory:

- **Low RAM** (`$0000-$07FF`): the SA-1 has its own copy of what the block uses, in two places. Page 0 is in I-RAM at the same addresses (the S-CPU sees it at `$3000`): nearly all direct-page accesses go there and I-RAM is the SA-1's fast memory. Pages 1 to 7 are in BW-RAM at `$40:0100-$07FF`, where code running with the data bank at `$7E` (now `$40`) finds them with absolute addressing; direct-page and bank-0 accesses to them are patched to go through the window at `$6000`. The SA-1's stack is in I-RAM too. All of it is copied across when the scene starts and back when it ends, shows the map or is quit (`low_full_in`, `give_back`). Per frame only the bytes the S-CPU's side of the scene also uses are moved, by straight-line code generated from the static analysis of the block, the loop head and the interrupt handlers (`low_tables()` in `tools/build.py` -> `low_in` / `low_out` in `build/blk_low.asm`): about 40 bytes in and 75 out, 0.03 vblank. Bytes the interrupt handlers also write come back only if the SA-1 changed them. `stale.lua` checks the analysis against what the S-CPU really reads and writes; `LOW_DROP="0014 0036" python3 tools/build.py` leaves bytes out to prove that check can fail.
- **`$7E:2000-$7FFF`** (road, object and HDMA tables, sprite lists, status display buffers, frame buffer): owned by the SA-1 for as long as the driving scene runs (`!own`), at the same addresses in bank `$40`. It is copied across once when the scene is set up (`drive_init`, the one place where DMA is allowed) and back by block move (`sync_out`, three frames) when the S-CPU is about to run anything else. The S-CPU's interrupt handlers read what they need of it from BW-RAM: hooks in the NMI handler switch the bank of the HDMA tables, the sprite upload, the frame buffer upload and two table copies; the status display's NMI routine (`$90:B337`, shared with the on-foot scenes) is run from the copy in the driving scene, with its pointers' bank bytes changed (`nmi_hud`, `build/hud_patch.asm`).
- BW-RAM is 64 KB (header `$06`). `$40:8000-$FFFF` belongs to the in-between frames (below): the shadow of the game's state, the object table as drawn, an in-between frame's sprite table. It has a battery, so everything the patch keeps there survives a power cycle: `boot` clears the flags, and **every other variable must be set before it is read**, each scene and each step. One was not (`!sh_slot`, which record `sbx_next` is to put back): with a leftover value the first step of a scene overwrote an object record, and the tests passed for as long as Mesen's `.srm` (`~/.config/Mesen2/Saves`) happened to hold `$FFFF` there; the video's own check ("the original plays a different game from step 1") caught it. `tools/run.py` now fills BW-RAM with garbage before the first instruction of every run (the same each time; `--bw-seed N` for other garbage, `--bw-keep` for Mesen's), so no run depends on the one before. Garbage alone would not have shown that bug (the stray write goes somewhere nobody compares): when adding a variable, look for its first read.

**The S-CPU must never be held up.** The driving scene splits the screen with five timed IRQs a frame whose handlers wait for the next horizontal blank and write PPU registers; on the original none starts more than 170 master clocks late. A DMA transfer stops the CPU until it is done (8 clocks a byte), so the per-frame copies are block moves (`MVN`, interruptible per byte, about 46 clocks a byte) and are kept small. An earlier version copied 15 KB a frame by DMA and garbled about one frame in seven. While the SA-1 works the S-CPU waits in a few bytes of code in WRAM (`$7E:1F00`), because the SA-1 is held up whenever both CPUs use the ROM at once.

Other things that had to be dealt with (`src/sa1.asm`, `src/offload.asm`):

- **The SA-1's direct page and data bank.** Code that runs with the data bank at `$7E` reaches low RAM with absolute addressing; on the SA-1 that data bank is `$40`, so pages 1 to 7 have to be at `$40:0100`. Page 0 is in I-RAM instead (see Memory): three instructions that reach page 0 through the `$7E` data bank go through trampolines that use a long address, and the generator reports any indexed access that could cross between the two.
- **The PPU multiplier and the S-CPU's divider** do not exist for the SA-1. Reads of `$2134-$2136` go to the SA-1's product register and writes of `$211B/$211C` to helpers that emulate the write latch; `$4204-$4206` / `$4214-$4217` go to variables and a helper that divides on the SA-1's arithmetic unit. The two hot multiply routines are replaced outright (`src/fastmath.asm`).
- **Sound** (`$81:DB9E`) is queued by the SA-1 and sent by the S-CPU afterwards. A DMA fill of work RAM (`$90:BD66`) is done by hand.
- **Pointers into `$7E` built from constants** (`LDX #$007E / STX $3D`) need the bank byte changed to `$40` (`--bankimm`), and the low RAM bytes that hold them are translated at the copy boundary (`LOW_BANK_BYTES`).
- **The frame buffer upload and the flip** (`nmi_piece`, `nmi_last`, `nmi_flipq` in `src/offload.asm`). The game's rule (whole `$400`s, `$C00` a vblank, flip only in a vblank that began with under `$400` left) made every finished frame wait one or two vblanks more. The replacement asks the PPU where the beam is (`$2137`/`$213D`, which the game does not use) and sends what fits: if the frame is complete and all of it fits before line 251, it is sent and shown; otherwise whatever has been drawn goes, in whole tiles, as far as it ends before line 258 (259 gained one frame in 364 and left 1.1 lines of margin; this leaves 2). The budget was measured on the original: 8.1 lines from the flip decision to `$00:8234` besides the last piece (5.5 now: `nmi_oam_hi` sends the sprites' high bits by DMA, not a byte at a time), and up to 9.6 more for gauge animations (6.1 in the demo; 9.6 seen in `play_drive`) that only run when `$59` is zero, so a vblank without that much room sets `$59` and they run a vblank later. A frame is never shown one vblank after the last (`!vb_since`). `vbudget.lua` fails the tests if a write comes within a line of the end of vblank, and `play.lua` if VRAM is not the frame buffer at a flip. The budget is in bytes at 170 a line, but code is not free: the decision itself takes about 1.5 lines of the vblank and every transfer's set-up most of one, so the limits carry that as slack (the lines-to-bytes multiplication is a table for that reason, and a transfer by itself is charged `!BOT_OVH`), and the tightest vblank in the tests ends 1.8 lines early.
- **Slots, and what `$DF` means** (`send_bot`, `fb_mark` / `obj_next`). The scaler draws into slots of 16 x 16 pixels, eight to a `$400` of the frame buffer: a slot's upper two tiles (`$40` bytes) and its lower two `$200` further on. `$DF` is where the upper tiles of the slot allocated *last* are (table at `$80:DE02`, by `$DD` - 2; with none allocated in a frame it is 0 and the last slot in use is the fourth, the gauges' needles). Two things follow, and the replacement upload had both wrong until Chris saw the result in the video (brief garbage in the road and the mirror on most frames):
  - Of a complete frame the `$400` that `$DF` stands in holds upper halves up to `$DF` + `$40` and lower halves from `$DF & $FC00` + `$200` up to `$DF` + `$240`: all beyond `$DF`. The game's last piece is always a whole `$400` and takes them along. Sending "up to `$DF`" left out the last sprite drawn and the lower halves of up to seven before it, which then showed what the frame before last had there. Now the last pieces go up to `$DF` + `$40` and the lower halves are sent by themselves, once per frame (`!bot_done`): with the piece that completes the frame if it cannot be shown yet, or else before the flip.
  - While a frame is being drawn, slots below `$DF` are not final either: an object of several slots allocates them all and then draws. The SA-1 therefore says how far it has finished each time the object pass has done with an object (`!fb_safe`, set at `$20:9F1A`), and pieces go that far, not to its live `$DF`. (Without it: once in the demo's 1,740 frames, two slots of a tall object were sent half-drawn and shown.)
  - No test saw the first because `play.lua` compared VRAM with the frame buffer up to `$DF` as well: the same wrong idea on both sides of the check. It now compares every tile of every sprite about to be shown. Lesson: check against what is on screen (sprites to tiles to pixels), not against the code's own notion of how much there is.
- The NMI handler reads how far the renderer has got (`$DF`) from the SA-1's copy while the block's second part runs (`!fb_sa1`), and which picture of the car is wanted (`$BD`) from the SA-1's copy always (`nmi_get_bd`). The car's tiles (`$600-$6C0` bytes, ten lines) are sent *instead of* a piece of the frame buffer on the original; here a piece follows in the same vblank when there is time, and the tiles are only sent in a vblank that has room for them and for what there is of the frame buffer to send; otherwise they wait, four vblanks at most (`!car_wait`).
- **Rewritten routines.** The hot inner loops run as new code on the SA-1, hooked into the copy, each leaving exactly what the game's own code leaves (the block tests compare every byte): the two multiplies (`src/fastmath.asm`), the road's main loop and second pass (`src/road.asm`: one SA-1 multiply per segment in place of 3 PPU multiplies and their retries, pointers stepped instead of recomputed), the road edges (`src/edges.asm`), the sort of the object list (`src/sort.asm`: an insertion sort on precomputed keys in I-RAM for the game's bubble sort). They use page-0 bytes the game leaves alone (`$02-$0C`, `$18-$25`) and I-RAM at `$0200`. `FASTMATH=0`, `FASTROAD=0`, `FASTSORT=0` switch them off one by one.
- **The on-foot scene's first NMI** (`foot_nmi_on` in `src/main.asm`, `NMIFIX=0` builds without). The scene's set-up runs with NMIs off for some 42 vblanks and turns them on at `$90:822B` whenever it is done; how long it takes varies (it talks to the sound CPU), and where in the frame it started depends on when the driving scene was left. If it ends during the vertical blank, the missed NMI is taken at once, late, and the handler's first VRAM and OAM uploads run on into the picture with the screen on (seen: NMI at line 261, uploads on lines 1 to 12), where hardware drops them. That is the original's own hazard, but the patch moves the dice, and one build hit it (`vbudget.lua` and both foot tests failed). The hook waits for the vertical blank to end and discards the missed NMI. It is the one patched instruction outside the driving scene.
- Asar assembles `BRA $008211` as a branch with offset `$11`. Branches to addresses in the original are written as `db $80,target-next`.

**Pipelining** (`src/pipe.asm`; `PIPE=0` builds without). A frame cannot be shown before its frame buffer is in VRAM, and only the vertical blank has time for that: about `$F40` bytes in the vblank that shows the frame, `$1400` in one that does not. The block draws into the frame buffer in its last third only, so run as one piece after the previous flip it has nothing to send at the first vblank and everything at the second, and any frame over `$F40` took a third. So the block is split at `$00:8EBA`:

- The *first part* (the car, the road and its HDMA tables, the status display: 60% of the time) touches neither the frame buffer nor the sprite tables. The SA-1 is started on it as soon as the frame before has been drawn, without waiting for that one to be shown (`try_early`, at the end of `blk_offload`). The *second part* (objects, scaled sprites) waits at the split point (`sa1_split`) for the S-CPU's word that the last frame is on show (`!go_b`). It is then finished well before the next vblank, which sends most of the frame; the one after shows it.
- The loop head's work for the frame is done early too: `try_early` samples the pad, or the demonstration's script, exactly as `$00:8C73` does, and gives the SA-1 the low RAM it would find after the waiting frame's flip (`$2C`, `$2E`, `$C5`, `$019B` are what the flip changes; `$DF`, `$C6`, `$DD`, `$E3`, `$7E` what the head resets). The head itself (`head_hook` at `$00:8C54`) then only waits for the flip, in work RAM, and carries on at `$00:8CA3`. Nothing is started early when Start is down, a fade is running or to come, or the map is up (`$0183`, `$0185`-`$0187`): then the head runs as in the original, so its ways out to the map and the title screen never meet a block in flight.
- **HDMA tables.** The game keeps two pairs of buffers and alternates (`$2C`); the first part of the next frame would overwrite the pair still on show. So at the split point the tables just built are copied to one of two pairs of *display buffers* (`$40:1100-$173F`), and the S-CPU is given those addresses in place of the block's `$2F/$30` and `$32/$33` (`!d_p1`, `!d_p2`; `LOW_SHOWN` in `tools/build.py` keeps the block's own values out of the per-frame copy). The block works on the same memory as ever. On a hand-back the display buffers are mirrored to work RAM at the same addresses (`sync_out`), which the game does not use.
- **`$80:9132`**, the block's fourth call, moves the gauges' needles: it draws into the head of the frame buffer and writes two sprites. That may only happen in the second part. But it shares scratch bytes (`$012B-$0138`) with the code after it, so it cannot simply be called later (tried: the block tests fail). Instead it runs where it always did from a *dry* copy (bank `$A1`, made by `dry_copy()` in `tools/build.py`: the SA-1's copy of the routine with the bank byte of every store into `$7E:2000-$7FFF` changed to `$C0`, which is ROM), and again for real at the split point from the same gauge positions (`sa1_g_dry`, `g_deferred`; `exit_g` when the block leaves the scene before the split point).
- While the first part runs, the S-CPU's own copy of low RAM holds the finished frame's values of everything (`low_out`), so the interrupt handlers show that frame from it undisturbed.
- Two things that went wrong on the way, both found by the tools: `!fb_sa1` was cleared after `try_early` had zeroed the SA-1's `$DF` for the next frame, so an NMI in between saw a complete frame with nothing left to send; and `!ex_...`/`!entry_p` were read after the SA-1 had been restarted (now copied to `!rx_...` first).

**In-between frames** (`src/sub.asm`; `SUB=0` builds without, and the game then runs four times too fast). The game's pass is run once per four shown frames, exactly as before, and shows its frame as before; `blk_offload` then has the SA-1 draw three more frames before it lets the game's loop head run again (`sub_frames`). So a game step lasts 8 vblanks (7.5 a second; the original took 6 to 11, 7.3 on average on the first drive and 8 in the demo), the game's logic sees what it always saw, and `play.lua` holds every step to the original's state and frame.

- **Drawn by the game's own code**: the road renderer, then the block's second part from `$00:8EBA` (the gun at the side window, scenery, the object pass) (`sa1_sub`, job 2 of the SA-1). That code moves, collides and animates as it draws (see the driving scene, above), and nothing in it is switched off. The second part is instead run again **from what the step's second part started from**, so it does again all that the step's did: at the split point of every step the objects' memory and the low RAM are copied aside (`pre_save`, called from `sa1_split`); an in-between frame's second part gets that copy of the objects' memory, and of the low RAM what the step changed after the split point (`low_diff` lists those words once per step, `low_split` puts them back), except what the frame's own first part has set since: where the car and the road are now. Sound commands queued meanwhile are dropped.
- **Why not switch the logic off.** The first version did: the enemies' state machines were skipped (what they leave for the drawing code recorded and put back), the collision test and the objects' approach were off, and the frame was drawn from the object table as the step left it. Every place where logic and drawing are one was then wrong for three frames in four, and Chris saw it at once in the video: an enemy blowing up (`$80:CEF6` counts the explosion on, draws that frame itself and never comes back to the drawing code) showed whole in between; type `$0A` added its own step again; thrown objects (`$80:AC0B`) and the muzzle flash (`$80:D0E2`) were a stage ahead; timers in low RAM (`$016D`, `$0193`, `$C0-$C4`) were a step ahead. With motion off 612 of the demo's 1,305 in-between frames were unlike their step's frame. Replaying from the split point's state makes "draws what the step drew" true by construction, for object types nobody has looked at as well.
- **What moves.** Things are moved on by 1, 2 or 3 quarters of a step, for the drawing only:
  - the car, by what the *next* step will move it if the buttons stay as they are. `predict` runs the next step's first two calls ahead of time, on the state this step left and the buttons held now: `$81B0E4` gives the next `$BB` and `$B1`, `$81B28A` the next `$AE`. The road is stepped that far before the frame's first part (`doctor`, as `$00:8DD3` does), and every object is drawn that much closer (`!sbx_adv`). With unchanged buttons the in-between frames lead into the next step's frame in four equal parts; an earlier version carried the *last* step's movement on, and every change of steering then arrived in one jump at the next step (measured with `smooth.lua`: steps across the road of 2, 2, 2, 9).
  - an object (types `$04`, `$0A`, `$0B`: what moves by itself), by what it moved along and across the road in this step (its place as this step drew it less its place as the step before drew it, the car's own `$AE` taken out; `sbx_capture` keeps the table behind each object pass; `doctor` works the shifts out into `!SHIFT`), if the record held the same kind of thing all along.
  - **where**: in the object's record, at the point where the pass has done with the object's logic and is about to draw it (`sbx_shift`, from hooks at `$20:9EEF`, `$9F2E`, `$C730`, `$CF35`), and the record is put back when the pass goes on to the next object (`sbx_next` at `$20:9F1A`). So the enemies decide, objects look at one another and collisions are tested at the places the step had them in. One thing the game decides before that point has to be decided again: by the *sign* of the distance an object goes the game's way for things ahead (`$9EEF`) or behind (`$9F2E`), and each way compares without sign from there on. An object the car passes between two steps arrived on the way ahead with a distance below zero, was taken for too far away to draw, and was missing from the mirror for a frame or two until the next step drew it there (Chris's glitches in the mirror were this as well as the upload). `sbx_far` and `sbx_behind` look at the sign after moving the record and send the object to the routine the game would use at that distance. A second version moved the records before the pass: an enemy then threw something in an in-between frame that the next step never saw, and collisions could show early.
  - the background (mountains, clouds): the road renderer scrolls it to `$60` = -`$64`/2 - 8 x `$B7`. `$64` is the heading, which `doctor` moves on; `$B7` is the steering rate, which changes once a step, and a change of 1 moved the background 8 pixels at the step and none in between (seen in the frames: 2, 2, 2, 10 through a bend). A hook in the renderer (`sbx_b7` at `$21:D414`) gives an in-between frame its quarters of the change `predict` expects: 4, 4, 4, 4.
  Fractions are cut towards zero, so what stands by the road stays on it. Nothing moves while the car rolls backwards.
- **The step's frame again when nothing is moved** (`SUBMOVE=0`): object for object and byte for byte, on the demo and the first drive. Three tools check it. `subobj.lua` / `subobj.py`: per object, what was written of the frame buffer and the sprite table while the object pass had it in hand, in the step and in each in-between frame. `subin.lua`: every byte the second part reads before writing, where an in-between frame finds another value than its step did (only the sprites' size bits at `$2F36`, which are stale and overwritten). `subchk.lua`: the finished frame buffer, sprite table, HDMA tables and display values. What is left in the demo is one step in 435 where the *view* differs: something moved the car after the step had drawn its road, and the in-between frames show it where it is.
- **The S-CPU's side** of an in-between frame is the loop head's display work (`$DC`, the upload counters) and handing over what the NMI handler shows a frame with (the HDMA tables' copies, `$5C`, `$60-$67`, `$C6`, `$DD`, `$DF`, `$E3`, `$019F`, `$01B0`, `$2E`, `$C5`); the game's own values of everything else stay as the step left them. The NMI handler shows every frame the same way, with two differences for an in-between frame (`!x_show`): it reads the sprite table from a copy (`!ST_D`; the real one is game state and put back), and `$2C`, which the game must find switched once per step, is switched back (`nmi_flip`).
- **Time** (`subtime.lua`): the copies cost 0.36 vblank before the first in-between frame, 0.2 before the others and 0.33 after the last; an in-between frame's road takes 0.85 and its objects 0.5. The first one is the tightest: the step's second part, the save, and its own first part should all fit before the step's frame is shown.

`tools/mkpatch.py` generates the patches to the copy (`build/blk_patch.asm`) and the lists of low RAM the block reads and writes. It walks the code reachable from the block's entry statically, taking M/X flags, direct page and data bank from the coverage trace where the code was traced and propagating them where it was not (with a model of the stack, for `PHB`/`PLB`). Jump tables, indexed accesses to low RAM, bank-byte constants and room for trampolines have to be given to it (`ROUTINES` in `tools/build.py`). **Its report (`build.py -v`) must show nothing but the eight computed jumps in the sprite scaler** (whose targets come from the trace); anything new there is a patch that is missing.

**How to debug a difference from the original:** `tools/test.py xcheck` or a block scenario gives the frame and the addresses. For the instruction where it goes wrong, build with `FASTMATH=0`, log the S-CPU's instructions (PC, A, X, Y) for one pass through the block on the original and the SA-1's on the build, and compare: they should match instruction for instruction, apart from the original's multiply retries, `$7E`/`$40` and `$80`/`$20` bank values, and direct-page values offset by `$6000`.

## Gameplay changes (`src/tweaks.asm`; `TWEAKS=0` builds without)

What players disliked is collected in `docs/outlander-complaints.md`. Each change is a number or two in `src/tweaks.asm`, to be tuned by Chris playing; Chris has played the build and ruled on the hit tests only so far. Nothing tests them but the measurements quoted here (scripts of the kind in `tools/hitbox.lua`; the driving ones read the SA-1's memory: page 0 in I-RAM, the rest at `$40:xxxx`, code at `$20:xxxx`).

Driving, as found:

- **Damage.** Everything adds to `$C0`, the damage of this pass, and `$00:8E19` takes it off the car's health (`$0404`, 511 at the start; `$0408` is armour, which takes it twice over first). `$80:B845` tests an object against the car (x within 42 + the type's width from the table at `$80:B8F7`; `$80:B8C3` says which types count) and calls the type's handler (`$80:B92B`): solid things (poles, cacti, rocks: types 2, 6, 7 and four of type 1's eight kinds, handler `$BA14`) stop the car dead and cost (speed - 6) x 8, which is 272 of the 511 at top speed (`$AE` = 41); a roadblock (types `$0C`, `$0D`, handler `$BBEF`) costs speed + 1 and `$60` of speed, and stops the car below speed 7; signs (type 0) cost the speed, small things half of it; what an enemy throws (type `$0B`) 12. Ramming and gunfire add to `$C0` elsewhere (`$80:B547`, `$80:D589`).
- **Obstacles are not placed by hand.** `$80:9A18` runs a round every 232 quarter segments travelled (`$014E`): three free records at most, filled in a fixed order of kinds, each kind on a countdown of its own (`$0150-$0158`) with positions from an additive random generator (`$80:98B5`, eight bytes at `$013F`). Nothing in it looks at the level. The striped roadblock in a lane is type `$0D` (x = 0 or +-100; counter `$0157`: 3 rounds without, 5 with, 1 to reload); type `$0C` is the same on the shoulder (x = +-248, every fourth round). Type 0 is the chevron in bends, 2 and 5 poles, 1 the roadside (cacti, rocks, wrecks).

Changed: roadblocks in a lane come in runs of 4 with gaps of 6 rounds (4 in 10 rounds for 5 in 9: 28% fewer; the shoulder's are as they were); 5/16 is taken off what one collision with something standing adds to `$C0` (the pole at top speed: 187), thrown things excepted.

On foot (`$90:824A`; all of it on the S-CPU, in work RAM, direct page `$0400`), as found:

- **Characters** are records of 16 bytes from `$7E:CB1D`; the player is the third (`$CB3D`, index register = `$20`). +0 x (word; the camera is the player's x, `$90:83A8`, and the player is drawn at screen x `$7C`), +3 y, +4 health (enemies; the player's is `$0404`, the car's own, with `$0406` taking three times the damage first: `$90:9033`), +5 flags (`$80` facing right for the player; `$10` crouching; enemies: `$80` a blow, `$40` a shot this frame, `$10` facing right), +8 bit 7 in use, +9 frames left of the animation frame, +`$A` sprite slot, +`$C` bit 0 move at the double, +`$D` pixels still to move (signed), +`$F` kind x 4.
- **Everything moves by its animation script** (`$90:978D`: words read through `[$37]`, top five bits an opcode from the table at `$90:97D8`). Opcode 17 (`$90:98D4`) gives pixels to move, `$90:99F6` pays them out at 1 a frame (2 with the flag). Walking is 6 pixels about every 5.9 frames.
- **Hit tests are distances between x positions**, nothing more: no height, no boxes, and the x is near a figure's left edge whichever way it faces, so the two sides differ. The player's blow (`$90:9249`, 20 damage): the nearest enemy in front, if less than 26 ahead of the player's x facing right (20 or 24 in some stances), or between 24 and 50 behind it facing left. An enemy's blow (`$90:8D8B` and a twin at `$90:8C7B`, 10 damage): the player less than 30 to its left or less than 60 to its right. Kind `$84` has a second blow (`$90:8BD1`, flag `$40`): the player from 30 up to 60 to its right, or from 6 up to 26 to its left. In gaps between the two bodies (measured on screenshots): the player reaches 14 pixels to the right and 28 to the left, an enemy 18 and 38, so there is a band on either side where it hits and the player cannot; an enemy overlapping the player on his left cannot be hit at all. An enemy's shot (`$90:8D00`) hits at any distance from 28 up unless the player crouches (every 85 frames from the gunner at the first scene); the player's shot (`$90:90D0`) takes the nearest enemy ahead within 135. `tools/hitbox.lua` draws all of this over the picture (in Mesen's window, or under `tools/run.py`).

Changed: the player's scripts move 1.5 times as far sideways and are paid out at 1 and 2 pixels in turn (`tw_setmove`, `tw_move`): 385 pixels in 300 frames for 257. The animation keeps its pace, and the jump and whatever else those scripts move goes 1.5 times as far too. - **The SA-1, now.** It draws four frames a step where it drew one, and in busy scenes it has no slack left. ## SA-1 conversion: constraints that shape everything

These are properties of the hardware. Check them against the reference project and an accurate emulator before relying on any one of them.

- The header must change to map mode `$23` and a cart type with SA-1 (`$35` = ROM + SA-1 + RAM + battery in the reference project), and the checksum must be recomputed.
- The SA-1 CPU cannot see WRAM (`$7E`/`$7F`, or its `$0000-$1FFF` mirror) or any PPU/CPU register (`$21xx`, `$42xx`, `$43xx`). It sees ROM, I-RAM (2 KB at `$3000-$37FF`, also at `$0000-$07FF` on the SA-1 side) and BW-RAM (`$6000-$7FFF` window and banks `$40+`). In Mesen, BW-RAM accesses cost the SA-1 an extra cycle and it is held up when both CPUs use the same kind of memory at once. So game logic can only move to the SA-1 if the RAM it touches is first relocated to I-RAM/BW-RAM, and anything that talks to the PPU, APU or joypad stays on the S-CPU or goes through a buffer.
- ROM banking is set by the Super MMC registers `$2220-$2223`, one megabyte per block. The game runs out of banks `$00` and `$81-$9F` (in the first 600 frames, 93% of instructions executed in bank `$81` and the rest in `$00`), and banks `$80-$9F` by default show the *third* megabyte. SA1-Root's 1 MB games write `$80` to all four registers, which puts block 0 in every region.
- The S-CPU does not get faster. The gain comes from running the expensive routines on the SA-1 (10.74 MHz) and having the S-CPU wait or present.

## Reference: SA1-Root (`~/Documents/repos/SA1-Root`)

A shallow clone of https://github.com/VitorVilela7/SA1-Root, Vitor Vilela's SA-1 conversions of Contra III, Gradius III, Super R-Type and Race Drivin'. This is the closest prior art there is: the same job done to four commercial games, with source. Read it before designing anything. The repository carries no licence file, so learn from it and credit it; do not paste its code in wholesale without asking the author.

**Race Drivin' is the one to study first** (`Race-Drivin/README.md`, `Race-Drivin/asm/`). It is a 1 MB LoROM first-person driving game that went from about 4.8 to 30 FPS. What it shows:

- *SA-1 as master.* The SA-1 runs the whole game. The S-CPU sits in a small loop copied into WRAM (`wram.asm`) and runs routines the SA-1 hands it through a pointer and flag in I-RAM (`$3180-$3183`; macros `call_snes`, `wait_snes`, `wait_ack` in `sa1_defines.asm`). `hooks.asm` redirects every routine that touches the PPU, APU or joypad into such a callback, and wraps single register writes (`set_register_a`). Calls can be asynchronous, which is where the parallelism comes from.
- *RAM remap.* `$0000-$00FF` to I-RAM `$3000`, `$0100-$1FFF` to BW-RAM `$6100`, `$7E:xxxx` to `$40:xxxx`. This is done by patching the operand of every instruction that addresses RAM: the `new_*_remap.asm` files are hundreds of KB of generated `org`/`dw` pairs, one family each for discrete, indexed and indirect accesses, plus hand fixes for `LDA #$7E` bank loads, `MVN` operands, DMA source banks and direct-page setup (`extra_remaps.asm`). They were generated from a disassembly plus emulator trace logs by the author's own tool ("SA-1 TLR"), which is not in the repository. Sites the trace never reached are marked `Analysis Missing!`, so coverage of the trace logs decides how safe the remap is.
- *Bring-up.* `sa1.asm` (`reset`) and `sa1cpu.asm` (`sa1_reset`): header bytes `$23,$35` at `$FFD5` and BW-RAM size at `$FFD8`, reset vector repointed, SA-1 vectors, bank registers, write enables, then the SA-1 jumps into the game's original init.
- *Hardware maths.* The game's multiply and divide routines are replaced in place with the SA-1 arithmetic registers (end of `hooks.asm`).
- *Speed is not the end of it.* Once accelerated, the game ran far too fast, because its physics advanced once per rendered frame. The fix was "Delta-Based Frame Correction" (`delta_*.asm`): count vblanks per rendered frame and scale every per-frame delta by it. It also removed frame-buffer delays and waits on NMI that capped the framerate whatever the CPU speed (`commit_buffer.asm`). Expect both problems in Outlander's driving scenes, and find out early whether its driving logic is tied to the render rate.

The other three READMEs each have a "Technical details" section comparing remap strategies: static operand patching (Super R-Type, Race Drivin') against remapping pointers at run time when the game passes RAM pointers around too freely to patch them all (Contra III, Gradius III).

All four are Asar patches applied to a copy of the original ROM (`asar sa1.asm game.sfc`), guarded by `assert read1(addr) == ...` so that a patch landing on unexpected bytes fails the build. Asar's `sa1rom` mapping, `pushpc`/`pullpc` and those asserts suit this kind of work, and this project should most likely use Asar the same way.

## Reference project: `~/Documents/snes-shooter` (Seraph Drive)

Chris's SA-1 homebrew. It was written for the SA-1 from scratch, where this project retrofits an existing game, so its architecture (SA-1 runs everything, S-CPU only presents) does not carry over directly. The pieces that do:

- `README.md`: build, test harness and profiler usage in full.
- `src/scpu.asm` (`reset`): the S-CPU sequence that brings up the SA-1: hold in reset via `$2200`, set the bank registers, BW-RAM/I-RAM write enables, the SA-1 reset/NMI/IRQ vectors at `$2203-$2208`, then release.
- `src/sa1.asm` (`sa1_reset`): the SA-1 side of start-up (stack `$37FF`, direct page `$3000`, its own write enables).
- `src/header.asm`: a working SA-1 header. `src/defs.inc`: register names for the PPU and the SA-1.
- `tools/xasm.py`: a dependency-free two-pass 65816/SPC700 assembler written for that project. It assembles whole ROMs; whether it can overlay patches on an existing image (`.incbin` then `.org` over it) has not been tried.
- `tools/mk_rom.py`: header checksum fix (hard-coded for a 4 MB image).
- `tools/emu.py`: headless libretro host: run N frames with scripted input, save screenshots/contact strips/audio, peek RAM. Works on any SNES ROM, so it can already drive the original game:

      SNES_CORE=~/.config/retroarch/cores/bsnes_mercury_accuracy_libretro.so \
        python3 ~/Documents/snes-shooter/tools/emu.py Outlander.sfc --frames 600 \
        --input "100-104:start" --strip 60 --out build/shots

- `tools/profile.py`: frame profiler built on `emu.py`. It is specific to Seraph Drive (reads SA-1 timer stamps from BW-RAM at `$40:5000`), but the method is the model for measuring this game: stamp a timer at markers, read the stamps from the host each frame, report per-section cost in scanlines and count dropped frames.

Copy tools into this repo's own `tools/` when they are needed and adapt them here; do not edit the shooter's copies for this project's sake.

## Emulator cores

In `~/.config/retroarch/cores/`:

- `bsnes_mercury_accuracy_libretro.so`: the timing-accurate one. Use it for anything about framerate, dropped frames or vblank overruns. It does not expose SA-1 I-RAM to the host, so debug values the host needs must be mirrored into WRAM or BW-RAM.
- `snes9x_libretro.so`: faster, exposes I-RAM, but does not emulate the SA-1 H/V timer.

`emu.py` defaults to an old Snes9x 1.54 core from another project's virtualenv; always set `SNES_CORE` explicitly.

## Tools installed for this project

- `asar`: Asar 1.91, built from `~/src/asar` (tag `v1.91`). SA1-Root's sources target 1.90.

Mesen debugs both the S-CPU and the SA-1 and, more to the point, runs Lua scripts with no window:

      mesen2 --testRunner Outlander.sfc script.lua

A callback on every instruction for 600 frames takes about four seconds. Note the flag is case-sensitive, and Mesen opens its first-run wizard instead (and fails without an X display) unless `~/.config/Mesen2/settings.json` exists; an empty `{}` was put there. The stream of `[CPU] Uninitialized memory read` lines is the game's, not an error; filter it out.
